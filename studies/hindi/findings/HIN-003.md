# HIN-003: Nukta letters have two encodings that NFC collapses, and standard Hindi spelling may drop the nukta in names

## Question and scope

How can one spoken name with a nukta letter appear in different Unicode strings, and which differences are removed by canonical normalization versus by orthographic variation? Scope: Devanagari (Deva) text of Hindi, hi-IN, PERSON; Unicode 16.0 data. Excludes rendering/fonts, other Devanagari languages, and any claim about other scripts of India. It matters because dictionary or gazetteer matching and offset mapping depend on which code point sequence is stored.

## Observation

Unicode defines U+093C DEVANAGARI SIGN NUKTA as a combining diacritic that derives letters such as क़, ज़, फ़ [HIN-S002](../sources.md#hin-s002) (fetch summary). It also encodes precomposed letters U+0958..U+095F (for example U+095B DEVANAGARI LETTER ZA). These have canonical decompositions to base consonant plus U+093C but are script-specific composition exclusions, so they do not appear in any normalization form [HIN-S003](../sources.md#hin-s003), section 5.1 (fetch summary). Local computation with Unicode data 16.0.0 confirms it: NFC and NFD of U+095B U+0940 U+0928 U+0924 both give U+091C U+093C U+0940 U+0928 U+0924 [HIN-S004](../sources.md#hin-s004). The same run shows that U+0929, U+0931 and U+0934 are not excluded: NFC keeps U+0929 as one code point while NFD splits it into U+0928 U+093C. So "nukta letters are always precomposed or always decomposed under NFC" is false; it depends on the letter.

Orthographically, the Central Hindi Directorate standard says the nukta is not current in Hindi, that Urdu-origin words assimilated into Hindi should be written in Hindi form without it, and that the nukta continues in transliterating Urdu source text [HIN-S001](../sources.md#hin-s001), section 3.15.1, printed p. 33 (decoded from an extraction with font artifacts). It is prescriptive, not a measure of usage. HiNER lists spelling variation among its challenges with a regional example (वनस्पति / बनस्पति) [HIN-S005](../sources.md#hin-s005), section 1, but the example is not a nukta case.

Confidence is **high** for the Unicode encoding behavior (standard plus local computation, though both standard pages were fetch summaries) and **medium** for the orthographic statement (one official source; no corpus frequency).

## NER hypothesis

Applying NFC before lexicon lookup and span mapping makes ex-01 and ex-02 identical without affecting ex-03, and a model trained on mixed forms without normalization treats ex-01/ex-02 as different inputs. Scope: boundary and span-offset consistency, not classification. Challenged if the tokenizer already maps both forms to the same pieces, or if NFC changes character counts so that stored offsets no longer align with original text (offset mapping is required in either case).

## Evidence handoff

Positive cases: each nukta letter in precomposed, decomposed and dropped form inside names. Hard negatives: non-name words with the same letters. Variation axes: encoding form, nukta presence, Unicode version. Destination: `ner-evidence`; deferred. Fixtures must record original code points; the normalized view must be shown separately.

## Evaluation handoff

Proposed slice `hi-nukta-forms`: same names in raw, NFC and nukta-dropped inputs with unchanged annotation; compare exact-span recall across the three. Do not treat nukta-dropping as a lossless transformation. Destination: `ner-eval`; deferred.

## Implementation options

Baseline: no normalization. Option: NFC at ingestion with offset map to original; option: separate nukta-folding feature used only for matching, never rewriting. Destination: `fastner`; deferred.

## Limitations and review

Which letters actually occur in Hindi names, and how often a given writer includes the nukta, is not measured. Both Unicode references were read only as summaries; the numerical claims come from the local run. Not tested on other Unicode versions. No reviewer.
