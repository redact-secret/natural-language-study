# TUR-003: Dotted and dotless I: locale-unaware case conversion corrupts Turkish names and breaks round trips

## Question and scope

What happens to names containing `İ`, `ı`, `I` and `i` when text is lowercased, uppercased or normalized by locale-unaware code, and how does that affect matching and casing cues for PERSON? Scope: Turkish written in Latin script (tr-TR); runtime behavior observed in one Python 3.14.7 environment. Excludes other runtimes and other Turkic languages (Azeri shares the mapping per the Unicode file but is out of scope).

## Observation

Unicode's SpecialCasing file contains language-conditional entries for `tr` and `az`: U+0130 lowercases to `i` (U+0069), U+0049 lowercases to U+0131 when not before a combining dot, and U+0069 uppercases to U+0130 [TUR-S003](../sources.md#tur-s003), as relayed by a fetch summary. The Snowball Turkish stemmer's rules treat U+0131 as a distinct letter [TUR-S012](../sources.md#tur-s012).

A local probe [TUR-S004](../sources.md#tur-s004) of Python's locale-free methods shows: `İ` (U+0130) NFD-decomposes to U+0049 U+0307 and NFC recomposes to U+0130; NFKC equals NFC for it; `'İstanbul'.lower()` returns `i` plus U+0307 plus `stanbul` (two code points for the first letter); `'ISPARTA'.lower()` returns `isparta`, not the Turkish `ısparta`; `'Işıl'.lower()` returns `işıl`; `'istanbul'.upper()` returns `ISTANBUL`, so the dot is lost; `'IŞIL'.lower()` returns `işil`. These are properties of default mappings in one runtime, not universal, and Python's method does not take a locale argument.

TDK says personal names begin with a capital letter [TUR-S002](../sources.md#tur-s002), so capitalization is normally a name cue in edited text; case folding that loses `İ` or turns `I` into `i` can change the string that gazetteers and lexicons see. Whether that harms NER was not measured.

Confidence **medium**: the Unicode and probe facts are firm for their scope, but the SpecialCasing lines were read via a summary and the NER effect is untested.

## NER hypothesis

Locale-aware case folding (or a fold that maps `İ/ı/I/i` consistently) will improve name matching and lexicon lookup relative to default folding on matched all-uppercase and normalization-variant inputs, without changing detection of already-correct mixed-case names. The hypothesis is challenged if a model sees no change because it never folds case, or if gains vanish on inputs already in NFC.

## Implementation options

Options: no change; apply tr-aware folding only for Turkish-tagged input; normalize NFD to NFC at ingest while retaining original-text coordinates; add a fold-insensitive lexicon key. Tradeoff: language identification dependence versus a language-neutral fold that conflates `I` and `İ`.

Destination: `fastner`; proposed experiments only, **deferred**; no downstream code was inspected for this finding.

## Limitations and review

One runtime only; Unicode lines read through a summary; no Turkish-locale behavior of other languages' libraries checked; no evidence on how often all-caps names occur in target data. The NFD observation affects any pipeline that normalizes but does not carry offsets back. Dictionary words that collide after lossy folding were not catalogued.
