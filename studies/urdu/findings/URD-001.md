# URD-001: Urdu names have Arabic-letter and Urdu-letter code point variants that Unicode normalization does not unify

## Question and scope

Can the same Urdu personal name reach a recognizer as different code point sequences, and does standard Unicode normalization remove the difference? Scope: Urdu in Pakistan, Arabic script (`Arab`), edited and typed text, entity type PERSON. Excluded: Nastaliq glyph shaping, fonts, other Pakistani languages written in Arabic script (Punjabi in Shahmukhi, Sindhi, Pashto, Balochi, Saraiki), and Roman Urdu (see [URD-005](URD-005.md)). The question matters because a model, gazetteer or tokenizer that sees different code points for one visually identical name sees different inputs.

## Observation

The Unicode Arabic block is extended for Urdu and other languages, and Urdu relies on letters such as yeh barree U+06D2 and Farsi yeh U+06CC that are distinct from Arabic yeh U+064A ([URD-S001](../sources.md#urd-s001), sections 9.2.1 and 9.2.4; summary read). Normalization forms NFC and NFKC are defined by canonical and compatibility equivalence ([URD-S003](../sources.md#urd-s003), section 1.2).

A local check with Python 3.14 `unicodedata` (Unicode data 16.0.0) shows that NFKC leaves each of these pairs unchanged and distinct: Farsi yeh U+06CC versus Arabic yeh U+064A; keheh U+06A9 versus Arabic kaf U+0643; heh goal U+06C1 versus Arabic heh U+0647. Hamza-bearing letters do decompose under NFD (for example U+06C2 to U+06C1 U+0654, U+0623 to U+0627 U+0654, U+06D3 to U+06D2 U+0654), so the same hamza letter can be precomposed or sequenced. Heh doachashmee U+06BE and teh marbuta goal U+06C3 are separate code points with no decomposition. This local run is an implementation observation, not a cited source claim; [URD-S003](../sources.md#urd-s003) itself, as read, said nothing about Arabic letters.

A published Urdu segmentation system preprocesses text by removing diacritics and normalizing input to remove encoding ambiguities ([URD-S004](../sources.md#urd-s004), section 3), which indicates the variants are a practical concern for Urdu pipelines. That source does not list which characters it folds.

Confidence: **medium**. The code point facts are mechanical and checked, but the frequency of the variants in real Pakistani Urdu text, keyboard defaults and OCR output was not measured, and chapter 9 was read as a summary.

## NER hypothesis

If a PERSON recognizer or gazetteer is trained or built only on one code point repertoire, then the same name in the other variant spelling (Arabic yeh, kaf or heh) will show lower recall than the matched primary-variant form, holding the name and context fixed; a fold-to-Urdu-letter step that is reversible for offsets will recover most of the difference without a matched-negative loss. The hypothesis fails if the recognizer already behaves identically on both variants, or if folding raises false positives on non-name Arabic-script text. Limits: it concerns surface representation, not whether a string is a name.

## Evidence handoff

Positive cases: matched pairs of the same fictional name in each variant. Hard negatives: strings that differ only by U+06BE or by hamza form and are different words. Variation axes: yeh, kaf, heh variant; precomposed versus decomposed hamza; with and without ZWNJ U+200C. Original strings and code points must be preserved and any folded text shown separately with the transformation named. Destination: `ner-evidence`; deferred pending language review and an offset-preserving normalization contract. No issue opened.

## Evaluation handoff

Proposed slice (proposal only): **urdu-codepoint-variants**, comparing recall on matched variant pairs against a canonical-form baseline with the model, split and scorer fixed. Failure condition: variant recall equals canonical recall within the evaluation's own noise. Destination: `ner-eval`; deferred until reviewed evidence exists.

## Implementation options

No-change baseline (consume input as-is) versus an offset-preserving fold of U+064A, U+0643, U+0647 to their Urdu counterparts for matching only. Tradeoff: folding may merge Arabic-script text from Arabic or Persian contexts and may alter hamza-bearing forms; any change must keep original coordinates. Destination: `fastner`; deferred, nothing inspected or executed here.

## Limitations and review

No keyboard-layout, OCR or corpus frequency evidence. No Nastaliq rendering analysis. The claim that ھ is a separate letter rests on the code point list, not a spelling authority such as the National Language Authority, which was not located.
