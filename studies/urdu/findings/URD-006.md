# URD-006: Following postpositions are a boundary cue but not a sufficient one, and maximal versus nested entity policy is unresolved

## Question and scope

How do postpositions such as `نے`, `کو`, `کا/کی/کے`, `سے`, `میں` and `پر` relate to the right edge of a PERSON span, and how should a person name nested inside a larger entity be treated? Scope: Urdu in Pakistan, `Arab` script (with Roman transliteration where the cited papers use it), news text as in the cited datasets, PERSON. Excluded: izafat constructions with `-e-` (named only as a gap), verb morphology, other Pakistani languages.

## Observation

One Urdu NER paper hypothesizes that in postpositional languages the postposition that follows a candidate decides whether it is an entity, using the example "Ali nay" and "Muhammad Ali nay", and proposes a tagging scheme (BIL2) that encodes it; it reports a lack of capitalization, agglutination, free word order and word segmentation as Urdu NER issues ([URD-S006](../sources.md#urd-s006), introduction and section IV). The authors compare tagging schemes on IJCNLP-08 data; their numeric results are not imported here. Another paper states a rule-based system that checks title, designation, surname and then following postpositions to resolve ambiguous names, and records that this fails when postpositions follow common nouns too ([URD-S005](../sources.md#urd-s005), p. 2516).

On nesting, the IJCNLP-08 task asks systems to find nested entities, with a Person nested inside an Organization as its example ([URD-S008](../sources.md#urd-s008)). Malik and Sarwar nevertheless annotate maximal entities, so a library name containing "Quaid-e-Azam" is tagged Location and the inner name is not tagged Person ([URD-S006](../sources.md#urd-s006), section V). The same paper's chosen policy therefore differs from the shared-task design, which shows that data are not interchangeable on this point. Treebank documentation describes tokens as whitespace-delimited with separated punctuation ([URD-S010](../sources.md#urd-s010)); whether postpositions are separate tokens in that treebank was not stated in the summary read, and the author's expectation that standard Urdu writes them as separate words is not source-verified here because the grammar consulted was only seen as a publisher description (see [sources](../sources.md#urd-s017)).

Confidence: **medium** for the existence of the cue and the nested/maximal policy difference; the cue's strength is untested.

## NER hypothesis

If a Urdu recognizer treats the next whitespace token as a postposition, then it will predict the right edge of a PERSON span more accurately than a window without that signal; but the signal will also trigger on non-person entities and common nouns, so it will reduce boundary errors only when paired with a name/non-name signal. A fixed-length name limit (three words) will truncate longer names. The prediction fails if removing the postposition feature changes boundary error or precision negligibly, or if the feature helps only on bare, short names.

## Evidence handoff

Positive cases: names followed by each postposition; four-part names; names inside organization and place names. Hard negatives: common nouns and non-person entities followed by the same postpositions (examples 05-06). Variation axes: postposition type, name length, nesting. Annotation choice (maximal or nested) must be decided downstream before any gold. Destination: `ner-evidence`; deferred.

## Evaluation handoff

Proposed slice **urdu-postposition-boundary**: hold the name fixed and vary the following word; report right-edge errors by following-token type and, separately, nested-inner recall under each policy. Destination: `ner-eval`; deferred.

## Implementation options

Whitespace plus lexicon of postpositions; contextual model features; a BIL-style tag scheme. Tradeoff: a tag scheme change affects training data compatibility. Destination: `fastner`; deferred.

## Limitations and review

The postposition list was not verified against a grammar. Izafat (`-e-`) compounds, honorific suffixes like `جی` and participial or oblique forms are not covered. Scores from the cited papers are not compared. No qualified reviewer.
